# Unity's D3D11 device on a D3D12 queue (D3D11On12)

VaM renders with a D3D11 device. NVIDIA's reconstruction (DLSS RR, SR through NGX D3D12, DLSS Frame Generation), the
path tracer (hardware ray tracing, shader model 6) and the denoiser all need D3D12. The mod therefore makes Unity's
device a D3D11On12 device: a D3D11 device whose work is translated onto one D3D12 direct queue that the mod can also
submit to. Nothing changes for VaM or Unity; the effect for a player is that all of the above can run inside the same
frame, in order, without a second queue or a fence. The price is CPU time in the translation layer and a set of rules that
keep D3D11 <-> D3D12 hand-overs cheap. Every number below was measured on the development machine unless said otherwise.

## How it works

### The proxy

`components/render/d3d11-proxy/d3d11_proxy.cpp` builds a `d3d11.dll` that sits next to `VaM.exe`. `UnityPlayer.dll`
loads `d3d11.dll` by name, so the copy in the exe folder wins. Every export except `D3D11CreateDevice` jumps to
System32's `d3d11.dll` (`d3d11_thunks.asm`, generated by `gen_thunks.py`, names in `d3d11.def`).

- `D3DINTEROP_MODE=on12` switches conversion on (the launcher sets it). Without it (or `pass`) every call goes to the real
  function, which is what "vanilla" and a failed start want.
- `Proxy_D3D11CreateDevice` converts only hardware calls with a `ppDevice` that come from `UnityPlayer.dll`
  (`ModuleName(_ReturnAddress())`). `CreateOn12` creates a D3D12 device on the same adapter, one `D3D12_COMMAND_LIST_TYPE_DIRECT`
  queue (named "D3DInterop 11on12 queue (Unity)") and calls `D3D11On12CreateDevice` with Unity's flags (the debug flag is
  dropped: it would need the D3D12 debug layer) and feature levels. If anything fails Unity gets the real device and a log line.
- The D3D12 device is a per-process singleton for the adapter: NGX, OFXR's DLSS-G and the NR pre-pass all use the same
  one. Only D3D11 contexts and D3D12 queues are separate. Other components find it with exports:
  `D3DInterop_GetOn12(device, queue)` (first device) and `D3DInterop_GetOn12ForDevice(device11, device, queue)`
  (checks that the given D3D11 device is Unity's). `VamOn12For`, `VamOn12ProcessDevice` in
  `components/render/opencomposite/OpenOVR/Compositor/vam_on12.h` wrap them.
- After the real `d3d11.dll` is loaded, the proxy renames its own loader entry to `d3d11_proxy.dll`, so
  `GetModuleHandle(L"d3d11.dll")` returns System32's DLL. Plugins that search that module's context vtable for a template
  (the skin plugin, hair shading) need that; with two modules named `d3d11.dll` they found none and lost their draw hooks.
  The loader's name hash still files the proxy under `d3d11.dll`, so `GetModuleHandle(L"d3d11_proxy.dll")` does **not**
  find it either: find it by enumerating modules for the export `D3DInterop_GetOn12ForDevice` (`VamOn12Proxy()`).
- On the desktop the same DLL also installs the presenter (`VamDesktopInstall`); see [frame-generation.md](frame-generation.md).
- `D3DINTEROP_LOG=<dir>` writes `d3d11_proxy.log` and samples the process's video memory once a second into
  `d3d11_proxy_vram.csv`.

### Handing a D3D11 resource to D3D12, and back

Everything from here is in `vam_on12.h`.

1. **Order.** D3D12 work executed on the 11on12 queue after a `Flush()` of the D3D11 immediate context runs after the
   D3D11 work recorded before it, on the same queue. No fence, no second queue, no CPU round trip. `VamOn12Commands` keeps a ring of 8 command
   allocators; `Begin()` waits only if a slot's last use is still running, `Submit()` executes after everything already on
   the queue, `Drain()` waits for the CPU. The first step of any hand-over is `context->Flush()`: unwrap itself
   submits nothing, so D3D11 work recorded before it would otherwise not exist yet for D3D12.
2. **Unwrap / return** (`VamOn12Unwrapped`). `UnwrapUnderlyingResource` gives the `ID3D12Resource` in COMMON state;
   `ReturnUnderlyingResource` gives it back. Buffers cannot be unwrapped (copy them, or create them in D3D12 and wrap them).
   **The queue named to the unwrap is 11on12's own only where that is proven safe.** The unwrap puts 11on12's residency
   signal on the queue it is given and, when D3D11 work on the texture is not yet submitted, a `Wait` for the command
   list that holds it. Given 11on12's own queue, that `Wait` sits ahead of the list's `Signal` and the queue never runs
   again (microsoft/D3D11On12 issue #51, fixed there 2025-09-25 by skipping the wait for its own queue). Windows 10 keeps
   the old `d3d11on12.dll`, and so does Windows 11 until an update brings the fix: the build Windows 11 24H2 first
   shipped with (26100.1) stops, 26100.9549 does not. A `Flush` before the unwrap does not help, nor does switching
   11on12's worker thread off (both tried with the probe below: the queue still stops).
   Naming a queue of ours that runs no work (`VamOn12UnwrapQueue`; the skin path tracer's `unwrapQueue`) works with
   every `d3d11on12.dll`: the D3D12 work still runs on 11on12's queue after the `Flush`, in order with the frame, and the
   other queue only takes the waits. But it cost about 5 % in VR without path tracing. On the dance scene on the
   simulated headset, frame generation off, it ran at 108.2, 110.0, 111.0, 104.0 and 109.7 fps naming 11on12's queue
   and at 102.3, 105.4 and 101.6 naming ours. Sessions with the same build vary by about 4 %. Path tracing was too noisy
   to tell, and the desktop showed no loss. The likely reason: 11on12's queue then waits on the other queue at each
   texture's next use. So the proxy runs
   `vamkit/bin/unwrap_probe.exe` at start-up, in a process of its own, on the `d3d11on12.dll` VaM loaded (an unwrap onto
   11on12's own queue, three rounds). Once it comes back, unwraps name 11on12's queue (`D3DInterop_UnwrapOnOwnQueue`,
   asked at every unwrap by `VamOn12UnwrapTarget` and the skin's `PathUnwrapQueue`). Before that (the first second or
   so), and for good when the probe stops (exit 2, it is ended) or cannot run, they name our queue.
   `D3DINTEROP_UNWRAP_QUEUE=own` / `separate` decides without the probe. `d3d11_proxy.log` names the `d3d11on12.dll`,
   the Windows build and the probe's verdict, with the DLL's version and the queue unwraps name. The probe tests the
   DLL itself instead of comparing version numbers: the first build with the fix is not known for any Windows release,
   and it differs between them (of Windows 11 24H2's DLLs, 26100.9549 has the fix and 26100.1, the one 24H2 first
   shipped with, has not).
3. **Textures used every frame are created in D3D12 and wrapped** (`MakeRrTexture(..., toD3d12=true)` in `vam_rr.inl`,
   `VamOn12Texture`): `CreateCommittedResource` (DEFAULT, UAV allowed, COMMON), `CreateWrappedResource(COMMON in, COMMON out)`,
   then `AcquireWrappedResources` once. Hand-over is `ReleaseWrappedResources` (a barrier at the next `Flush`) and
   `AcquireWrappedResources` afterwards. A texture that is wrapped and acquired when not on a D3D12 list costs no queue syncs.
   The RR input, albedo, normal, specular, depth, output, specular-distance, before-transparency and detail textures work this way;
   only the motion-vector texture belongs to the guide code and is still unwrapped once per eye.
4. **Never free a wrapped texture the GPU may still use.** D3D11 does not know D3D12 is reading it. `DropRrTexture` first waits for
   the queue (only on size changes, route switches and when detail preservation is toggled).
5. **Shared-resource matrix** (for textures that must also open in another device): created in D3D12 and opened in D3D11 works
   only for tier-1 formats with `ALLOW_RENDER_TARGET`; created in D3D11 (`MISC_SHARED`, KMT) and opened in D3D12 works for all
   colour formats (including RG32F) and all buffers. Creating a KMT-shared resource with a non-shareable format on an 11on12
   device removes the device. The NR pre-pass uses RG16F motion vectors for that reason.
6. **Constant buffers written every frame or draw are DYNAMIC and written with `Map(WRITE_DISCARD)`** (`VamWriteConstants`).
   `UpdateSubresource` on a DEFAULT constant buffer is a copy between two barriers under 11on12 (about 1.6 microseconds of GPU idle each,
   about 0 on native D3D11).

### Phased compute (hair, cloth, wraps)

Many small dependent compute dispatches serialise under 11on12, because the layer inserts a UAV barrier before a dispatch whose
UAVs were used earlier in the same command list, and on NVIDIA such a barrier waits for all earlier work. A `Flush()`
between phases starts a new command list, so every buffer is back in COMMON and the dispatches of *different items* in
the next phase need no barrier and run side by side. The three runtime components do this with items interleaved phase by
phase: `solveBatch` in `components/runtime/hair-solver/plugin/native/hair_solver_native.cpp`,
`components/runtime/cloth-physics/plugin/native/cloth_physics_native.cpp`,
`components/runtime/wrap-batch/native/wrap_batch_native.cpp` (`WB_RenderEventFunc` is just that flush).

### Textures the path tracer reads

The path tracer reads about 80 material textures a frame. Borrowing each from D3D11 every eye made the render thread issue
about 1800 sync events a frame (about 2.5 ms) and left the GPU idle before each eye's trace. `components/shading/skin/native/path_textures.inl`
copies a texture that D3D11 can only write by copy, `UpdateSubresource` or discard (no render target, UAV, depth or CPU access) into a D3D12
texture of its own, once, and binds that copy from then on. It watches seven slots of the immediate context's vtable
(`CopySubresourceRegion` 46, `CopyResource` 47, `UpdateSubresource` 48, `ResolveSubresource` 57, `CopySubresourceRegion1` 115,
`UpdateSubresource1` 116, `DiscardResource` 117); a write to a watched original marks it for another copy before the trace uses
it again. Render targets and the like are still borrowed, once a frame. No new copy is made when the process is within 2 GiB of its
video-memory budget (`kPathCopyReserve`); at most 16 copies and 512 MiB per frame, so a scene's first copies spread over frames.

### Without the proxy

Components that can run on native D3D11 must: one D3D11 -> D3D12 round trip per frame, at the end of the frame; resources
shared from D3D11 with KMT.

## Settings

| Where | Key | Values | Meaning |
|---|---|---|---|
| environment | `D3DINTEROP_MODE` | `on12` / `pass` / unset | convert Unity's device or not |
| environment | `D3DINTEROP_LOG` | directory | proxy log and VRAM sampling |
| environment | `D3DINTEROP_ON12_WORKER` | `0` / unset | a diagnostic: `0` creates the device with `D3D11_CREATE_DEVICE_PREVENT_INTERNAL_THREADING_OPTIMIZATIONS`, so 11on12 translates and submits on Unity's render thread instead of a worker thread of its own (checked with a small program: the one thread started in `d3d11on12.dll` is gone with the flag, `SINGLETHREADED` alone keeps it). The render thread then carries that thread's time |
| compile time | `kPathCopyReserve`, `kPathCopiesPerFrame`, `kPathCopyBytesPerFrame` in `path_textures.inl` | 2 GiB, 16, 512 MiB | resident-copy limits |

## Measured

All on a simulated headset unless noted (a stand-in OpenXR client; it has no real encoder or timewarp), a heavy two-character
dance scene, unless noted.

|---|---|---|

## Pitfalls

| Symptom | Cause | What to do |
|---|---|---|
| The picture freezes at the first DLSS / XeSS / FSR / RR frame or the first path-traced one (seen on the desktop; VR runs the same unwraps); GPU nearly idle; `dlssg.log`: `desktop wait: ... Unity's frame (the ready fence)` with Unity's queue stuck at one value and the presenter's queue drained; `opencomposite.log`: `NR GPU completion timed out` (or `11on12 GPU work timed out`) every 11 s. Windows 10, or a Windows 11 without Microsoft's fix | `UnwrapUnderlyingResource` naming 11on12's own queue: the old `d3d11on12.dll` puts a `Wait` ahead of its `Signal` there (see "Unwrap / return") | name 11on12's queue only after the proxy's probe has cleared the DLL, a queue that runs no work otherwise; read the probe's line in `d3d11_proxy.log`. `unwrap_probe.exe own` (`own dll <path>` for another DLL) tells whether a `d3d11on12.dll` has the bug; an old one copied beside `VaM.exe` in a test copy reproduces it in the game (the D3D11 runtime loads `d3d11on12.dll` from the application folder first; Windows keeps old builds in `WinSxS`) |
| `GetModuleHandle("d3d11_proxy.dll")` returns null | the loader entry was renamed but the hash was not | enumerate modules for `D3DInterop_GetOn12ForDevice` |
| A plugin that searches `d3d11.dll`'s vtable finds no template | two modules called `d3d11.dll` | the rename above exists for this |
| Device removed right after creating a shared texture | KMT-shared with a format that is not shareable under 11on12 | create in D3D12 and wrap, or pick a tier-1 format |
| Frame time rises by 0.5 ms or more with many small updates | `UpdateSubresource` on DEFAULT constant buffers | DYNAMIC + `Map(WRITE_DISCARD)` |
| GPU waits before every eye although each dispatch is small | many per-texture unwraps | create in D3D12, wrap once, or copy once into a resident D3D12 texture |
| Dependent compute from several items runs one after another | UAV barriers in one command list | phase the work and `Flush()` between phases |
| Removing the fence from unwrap/return did nothing | the cost is the sync sequence per resource, not the fence | reduce the number of resources handed over, not the fences; return without a fence only when the D3D12 work is on the 11on12 queue itself |
| Use-after-free after a resolution change | wrapped texture deleted while D3D12 still read it | `DropRrTexture` waits for the queue |
| NVIDIA NGX on D3D11 SR fails (`0xbad00002`) | not supported on 11on12 | SR runs on NGX D3D12 with unwrapped textures |
| Variable-rate shading unavailable | NVAPI D3D11 VRS needs a real D3D11 device | none; `FFREnabled` is fixed 0 |

## Tried and dropped

- **A full D3D12 port of VaM** (`-force-d3d12` with a patched `UnityPlayer.dll`: four patches for the OpenVR graphics API whitelist, compute
  shader variant lookup, tessellated hair that was dropped, and compressed texture row counts, plus a translation layer for the
  eye textures). The development tree also had it; it is not in this repository and
  VaM's own `UnityPlayer.dll` is never modified. At the same 4x scenario both designs ran at 27.8 ms per real frame, but with frame generation
  off the port was slower (93.8 vs 122.6 fps in one scene, 104.5 after optimisation; the bottleneck was Unity's D3D12 render thread, 9.8-15.2 ms
  vs 6.6-8.3 ms per frame). Unity 2018.1's D3D12 backend also hit two errors of its own: index, rigid-vertex and UV buffers are
  `DENY_SHADER_RESOURCE` (an SRV removes the device, so they must be copied), and its shadow comparison sampler is GREATER, not LESS_EQUAL; SPS stereo is unavailable (multi-pass
  only) and `-force-gfx-jobs native` removes the device after a while. Shader-visible descriptor heaps are write-combined memory: after copying descriptors into one, any `lock`-prefixed instruction waits for the write-combining buffer to drain (about 130 ns each). The only thing the port had that 11on12 lacks is shader model 6 and native variable-rate shading inside VaM's own draws, which this mod does not use.
- **Concurrent queues for the denoiser and SR** beside rendering: see [frame-path.md](frame-path.md).

## Open

- The hardware-threading cost of the translation layer was measured as busy time; a per-frame attribution of how much of the
  extra render-thread time is hidden by VaM's idle waits was not made.
- Heavy CPU-bound scenes where the extra 2.7-2.9 ms render thread time could matter were not measured.

## Verify

- Start with `D3DINTEROP_LOG` set and read `d3d11_proxy.log`: the line `on12: device ... on D3D12 device ... queue ...` and
  `D3D11CreateDevice from UnityPlayer.dll ... (11on12)`. `(real D3D11)` means the conversion did not happen.
- Sync cost and GPU idle can only be seen with GPU event tracing: `logman start <name> -p Microsoft-Windows-DxgKrnl 0x1 0xff -o x.etl -ets`, `logman stop <name> -ets`,
  `tracerpt x.etl -o x.xml -of XML` (a "Performance Log Users" member suffices; look only at VaM's own queues, since the
  desktop compositor and other apps keep packets queued too). The development tree had two scripts for it; this repository has none.
- The compositor's `VAM GPU timing` log lines (every 10 s) split a frame into stages and report per-eye GPU times.
- Only a real run shows the result; there is no offline test of the 11on12 layer in this repository.
